# Changelog

## Unreleased

- Test infra (0.4.2): the predicate differential test ids no longer contain a backslash. mutmut's fork server runs a warm-up `--collect-only` and then selects tests by explicit node id in the same process, and pytest cannot select an id with a backslash on the second in-process invocation (usage error 4: `not found`), which failed the "Running clean tests" phase of 47 of 50 mutation shards.
- Fix (0.4.2, TS differential): `intent_v2_active` now also returns true for a PRESENT but malformed v2 context (e.g. `policy.session.require: "yes"`), as documented ("true iff any v2 check would be reported"): `decide_intent_v2` reports failing checks for that context, so a host gating v2 enforcement on the helper used to skip it (fail open). The shared `k042-intentv2-cases` oracle was regenerated from the fixed reference.
- Fix (0.4.2, TS differential: the shared predjs / actionschema / intentacc / mapartcls / oracleprov / wbmisc / sessrevoc / killPred oracles, 7,000+ new cases): (1) a `not` chain deeper than ~250 levels exhausted the interpreter stack and the condition came back `unknown`; the reference decides it, so `not` chains are now unwound iteratively and `all_of` / `any_of` recurse one frame per level (`evaluate_condition_tri`, `test_k042_killpred_diff.py`); (2) `schema_verb` raised on any non-object entry of `verbs`; the reference skips a string / number / array entry (`"v".verb` is undefined) and only throws on `null`, so `conform_action` of a schema with such an entry now reports `unknown_verb` / the verb it finds instead of raising; (3) reason texts spelled a JSON value with Python's `repr` / canonical-JSON number text: they now use `String(x)` (a list as `a,b`, `NaN`, `Infinity`, `1e+21`), e.g. `'a,b' is revoked`. New differential tests `test_k042_*_diff.py` and unit tests of the `_js_string` / `_action_member` helpers.
- Fix (0.4.2, TS differential): `decide_intent_v2` read `aud`, `action`, `action.verb`, `action.resource` and `action.params_digest` with `[...]`, so a PCActn missing one raised and the check failed with `... error (fail closed): '<key>'`. It now reads them like the reference (`p.action?.verb`, `String(...)`): a missing `resource` no longer fails `intent_session` (TS passes it), and a missing `aud` / `action` gets the reference's reasons (`schema aud does not match the PCActn aud`, `params do not hash to action.params_digest`, `the session schema is for another audience`). New `test_mutation_kill_intent_v2_diff.py` runs the shared `k042-intentv2-cases` oracle (1,009 cases agree). Note: in the Python API a `None` v2 context is the ABSENT context; a JSON-null context (malformed in TS) has no separate spelling.
- Security / Breaking (0.4.2, R3-01): a pure post-quantum or hybrid Intent Layer v2 session root verifies only under the VERIFIER's pin for its signer, the new verifier-context member `session.pq_pins` (`{<ed25519 key>: <pq_pk>}`), never under the root's own `principals[].pq_pk`. No pin fails closed (`session root suite '<alg>' needs the signer's PQ key pinned by the verifier (pq_pins) ...`), a pin that differs from the root's `pq_pk` fails, and a signer principals entry that declares another key fails. A malformed `pq_pins` (not an object of strings) is a malformed session context. Ed25519 roots are unchanged. Conformance `session-root-*-unpinned`, `-pin-mismatch`, `-pin-other-signer`, `-principal-entry-mismatch`, `ctx-session-pq-pins-*`. `verify_session_root(s, pq_pins)`.
- Security (0.4.2 audit): `require_pca` no longer echoes the verdict reason into `WWW-Authenticate` (it can carry attacker-controlled text, so CR/LF reached the header). The 403 challenge is `PCA realm="pca", audience="...", error="insufficient_authority"` (TS `requirePCA` puts no reason in its challenge either); the reason stays on `PCAResult.verdict` / `error`.
- Fix (0.4.2 audit): a `grant_ref` that is not a string (absent, null, list, dict, number) is a 401 `invalid_pcactn` / `malformed PCActn` and never reaches `resolve_grant` (as in TS); a `resolve_grant` that raises fails closed with a 403 (`resolve_grant_error`) instead of escaping as a 500.
- Fix (0.4.2 audit): the Intent Layer v2 "unsupported suite" classification is a structured signal (`UnsupportedSuiteReason`, minted only by `suite_capability_error`) instead of a substring test, so a shape error that echoes a member named `unsupported_suite` (e.g. `key set: unknown member 'unsupported_suite'`) is no longer reported as an unsupported-suite refusal; it is `invalid`. Reason texts are unchanged.
- Fix (fail closed, standalone chain API): `verify_chain` given BOTH the verifier's stored grant (trusted root) and a PQ pin for the root issuer authorised the root on the stored grant and ignored a pin that names a different key. Both must now agree: a disagreeing pin refuses with `hop 0: root suite '<alg>': the server-side PQ pin for the root issuer (policy.pqPins) does not match the stored grant's pq_pk (fail closed)`, as in the TypeScript reference. The PCActn verify path passes only the stored grant and is unchanged. New shared vectors `chainpin-pure-pq-root-trusted-root-and-matching-pin`, `chainpin-pure-pq-root-trusted-root-wrong-pin`, `chainpin-hybrid-root-trusted-root-wrong-pin`.
- Rule 15 key-set equivocation (5501b545): the tracked `acc.keyset_versions[root]` is exactly `{version, digest}` (`tracked_key_set_error`; anything else makes the acc context malformed); a presented key set is skipped when its version is below the tracked one or equal with another digest (`sequencer_key_set_digest`). Rule 13: the revocation evidence and the tracked last epoch are closed `{epoch, revoked}` (an extra member is refused); the `intent_revocation` runner and the diff-fuzz driver build the evidence from every input member except the check parameters.
- Intent Layer v2 batch 2. Rule 19 (V15, committed map): `intent_session.map_form` ("commit" only; anything else fails `wire`) selects the `pca-intent:v2c:<session>:<map_commit>` goal (`intent_goal_commit` / `decide_intent_binding` take `map_form`), and the new check `map` (after `accumulators`, before W-B; reported iff the commit form or `policy.map.require`) runs the Z0 disclosure decision over the context member `map: {disclosure}`: new module `atlas_pca.intent_map` (salted kind-tagged leaves, RFC 9162 openings, closed and typed header / cell / metrics / learner leaves, the exact cell of the action, `decide_map_disclosure`, `commit_leaves`, the `commit_map` builder). The v2 policy is closed to `{session, schema, acc, map}` with `policy.acc {max_receipt_age_s?, max_keyset_age_s?}` and `policy.map {require?, max_residual_risk_ppm?}`. Rule 15: a receipt lives at most 15 min and must be at most `max_receipt_age_s` old (default 900 s); key sets carry a monotone `version` (>= the tracked `acc.keyset_versions[root]`) and are at most `max_keyset_age_s` old (default 3600 s); a retired key (`not_after < now - 60 s`) stops verifying. Rule 13 step 7: `S.revocation.key` is a required DEDICATED authority (never a principal, the only epoch signer, PQ only under `S.revocation.pq_pk`); the evidence is `{epoch, revoked}` with the full sorted revoked set (`revset_root`), append-only against the tracked `session.revocation_last` (no rollback, no drop); `check_session_revocation(ev, session=, authority=, ids=, now=, max_age_ms=, last=)`. Suites resolve through the runtime dispatch (`suite_available`). The W-B entry points never raise (a non-object input fails `facts`: "the W-B context is malformed: input must be an object"; an internal error is a `facts` failure; `decide_offer_set` validates its policy). Runners: `intent_revocation` in the new form, `intent_map_commit` and `intent_map`, `requires_suite` outside the manifest asserts the `unsupported_suite` refusal, and every primitive reads `input_json` (raw JSON text, `-0` kept) when present; the diff-fuzz driver answers every `intent_*` primitive kind. Kills in `test_mutation_kill_intent_v2.py`.
- Suite capability (packages/pca/conformance/SUITES.md): new `atlas_pca.pq_backends` - ML-DSA-65 / ML-DSA-87 (FIPS 204) through dilithium-py (extra `pq`) or OpenSSL >= 3.5 libcrypto, SLH-DSA-SHA2-128f / SLH-DSA-SHA2-256s (FIPS 205) through OpenSSL >= 3.5 libcrypto (ctypes; ATLAS_PCA_LIBCRYPTO override; real per-key-type probe), pure mode, empty context. The suite dispatch covers all of them plus the `hybrid-ed25519-*` forms and the SUF-CMA `hybrid-nested-ed25519-ml-dsa-65`, with per-suite lengths on the leaf, capability hops, threshold shares and pq artifacts. A registered suite this runtime cannot verify (`fn-dsa-512`, `fn-dsa-1024`, `less-cat1`, `hybrid-ed25519-less-cat1`, or a PQ suite whose backend is missing) fails closed with the distinct reason `unsupported_suite: <alg>`; an unregistered alg keeps `unknown signature alg`. Manifest: `REGISTERED_SUITES`, `supported_suites()`, `suite_available(alg)`, `UNSUPPORTED_SUITE`. The conformance runner asserts `unsupported_suite` instead of skipping; the diff-fuzz driver answers kind `suites` and tags `unsupported_suite` verdicts.
- Intent Layer v2 W-A (rules 13-15) and the v2 pipeline: the optional SIGNED top-level `intent_session` member (closed set `session, root, seq, schema, acc, facts, offer_set, prov, classes, labels`; `session` / `root` / `schema` 32-byte digests, `seq` a safe integer in [0, 2^31-1], `acc` <= 16 distinct `{id, post, receipt?}` claims, `facts` / `classes` / `labels` <= 16 / 8 / 16 distinct digests, `prov` <= 32 `action.params.<name>` paths of 1..8 strings of <= 256 UTF-8 bytes) is validated in `wire`. - Intent Layer v2 strict pass (reference 5e0a33a9): every v2 number is a safe integer (never -0, null, a string or a fraction) and the verifier clock must be one too, else every v2 check fails; every list is a real JSON array; keyed reads are own members only; `__proto__` / `constructor` / `prototype` are refused as accumulator ids, monitor ids and schema parameter names; a `null` parameter `default` is malformed. Absent vs null: an absent optional member is empty / default, a present `null` (or wrong JSON type) is malformed, in the verifier context and in every v2 artifact (`S.layers.org` / `std` null are now refused); a malformed top-level context member fails `schema`, `intent_session` (and `accumulators` with the member) with `malformed v2 context: ...` (`intent_v2_context_error`; the `wb` part is `intent_wb.validate_wb_context`). ## 0.4.1 - 2026-10-12

- Security (policy layer): caveats on the root grant outside the envelope are now evaluated like delegated caveats; new policy_caveats/evaluate_caveats helpers (incl. max_spend). The core verifier still does not evaluate caveats. `policy_caveats(grant, chain)` = the grant's caveats without its first `envelope` caveat, then the caveats the hops appended; `evaluate_caveats(caveats, ctx) -> (ok, failed)` is total. New corpus table `caveat_eval`.
- Threshold share signatures are validated per suite in `wire`: `alg` absent = ed25519 (64-byte `sig`, no `pq_sig`), `ml-dsa-65` (3309-byte `sig`, no `pq_sig`), `hybrid-ed25519-ml-dsa-65` (64-byte `sig` + 3309-byte `pq_sig`); a non-string or unknown `alg` fails. A share's `pq_pk` stays an optional echo judged by the threshold check. Before, every share `sig` had to be 64 bytes, so a pure ML-DSA-65 share could not be carried. New helper `validate_share_signature_wire`. The conformance runner skips vectors whose `requires` names a suite this package does not implement (ml-dsa-87, slh-dsa-sha2-128f).
- The `PCA-Action` header is decoded by the new public `decode_pca_header` (raises `PcaHeaderError`): strict unpadded base64url (no padding, standard alphabet or whitespace anywhere, nothing trimmed, canonical trailing bits) then strict UTF-8 with a leading BOM kept. The guard already decoded strictly; it now goes through this one decoder (same 401). New corpus table `pca_header`.

## 0.4.0 - 2026-10-11 (BREAKING)

- Depth / strict digests (security, parity): every protocol digest (`hash_canonical`: capability / grant hash, hop body digest, caveat comparison, params and conditions digests; Merkle leaves) now uses the STRICT canonical form like the reference (`hashCanonical` is `canonicalizeStrict`): nesting depth <= 32, safe integers only, plain decimals, no lone surrogates. It was the lenient form, so a correctly SIGNED hop carrying a depth-33 value, `1e300`, `2^53+2` or a lone surrogate verified although the reference refuses the chain (and the lenient form recursed without bound). Such hops are now refused (`hop N: malformed body`). `hash_canonical` raises `TypeError` on out-of-profile input, like the reference. `verify_leaf_suite` is total.
- R6-03 / R6-04 (security, parity): `verify_threshold_share` validates the WHOLE signer set like the TypeScript reference before looking at the share: unknown roles, non-canonical / non-32-byte public keys, and an empty, null, short or non-canonical `pq_pk` ANYWHERE in the set now refuse it; one key per role and one role per key; a duplicate (role, key) entry is accepted only with the same `pq_pk` (a conflicting one used to resolve first-wins); `t` must be 1, 2 or 3 (0..255 was accepted); `share.role` must equal the role. New corpus tables `threshold_set` / `signer_set_hash`.
- R6-05: `verify_chain`, `verify_threshold_share` and `verify_pcactn_core` are TOTAL: malformed input (non-object hop, missing or wrong-typed fields, truncated base64url, huge numbers) is a deny, never an exception. `verify_chain` also applies the reference hop type check (string id/issuer/holder/body_digest/sig, optional alg/pq_pk/pq_sig/holder_pq/parent absent or string, caveats a list of objects with a string `type`), so a correctly signed but ill-typed hop is now refused. New corpus table `malformed`.
- R6-02 (security): a signer-set role that registers a `pq_pk` now REQUIRES a PQ (pure or hybrid) threshold share; an ed25519-only share for that role is refused, so an Ed25519 break no longer forges a hybrid-registered role (parity with the TypeScript reference). Corpus: `agent-bound-signerset-with-pq-pk` is now `valid:false`; new positive `agent-hybrid-signerset-with-pq-pk`.
- R5-A1 (security): threshold-share verification is now signer-set PINNED, no longer self-vouched. The share must be for the one key the signer set registers for its role, a PQ/hybrid share verifies only under the set's registered `pq_pk` (a differing share `pq_pk` is refused), the share-suite tag is part of the signed bytes (a classical share cannot be relabelled hybrid), and the signer-set hash now includes a registered `pq_pk` (parity with the TypeScript reference). New corpus vectors: `agent-not-in-signer-set`, `agent-bound-signerset-with-pq-pk`, `agent-hybrid-relabel-*`.

- Suite policy defaults documented: no list = no restriction, an empty list refuses everything, and the hosted API defaults to ed25519 + Ed25519 hybrids (README lists the exact list to pass offline).

- R4-01: `verify_chain` now takes the root's PQ authority from the verifier, exactly like the TypeScript reference (R3-01). A non-ed25519 (pure `ml-dsa-65` or hybrid) ROOT hop is accepted only if the new `pq_pins` argument maps `root.issuer` to the root's own `pq_pk`, or the new `trusted_root` argument is the root itself (same content hash, i.e. the verifier's stored grant). Otherwise it is refused with `hop 0: root suite '<alg>' needs a PQ key pinned for the root issuer (policy.pqPins) or the verifier's stored grant (policy.trustedRoot); the root's own pq_pk proves nothing about who issued it (R3-01)`. Before, a pure-PQ root signed with the attacker's own ML-DSA key but naming a victim Ed25519 issuer verified. Callers of `verify_chain` on a root they did not load from their own store must now pass `pq_pins`. `verify_pcactn_core` is unchanged in behaviour (it passes its grant as `trusted_root`). Internally one `_resolve_pq_key` choke point mints the only key type `_verify_suite` accepts, so the PQ verify cannot be called with an artifact key.

- R3-03: the verifier now enforces the F-2 `holder_pq` binding exactly like the TypeScript reference. A hop (index >= 1) or the PCActn leaf signed under `ml-dsa-65` / `hybrid-ed25519-ml-dsa-65` is accepted only if its `pq_pk` hashes to the signer's `holder_pq` commitment; an unbound or attacker-chosen PQ key now fails (`chain` / `leaf_signature`). Hops may carry `holder_pq` (32-byte base64url, part of the signed body). New optional `allowed_suites` argument on `verify_pcactn_core` / `verify_chain` (a present list, even empty, enforces). Natives have no `allowUnboundPq` switch.
