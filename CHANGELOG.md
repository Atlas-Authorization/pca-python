# Changelog

## Unreleased (0.5.0)

- **Breaking (provenance by default):** `authorize` and the guards run a new `provenance_flow` check on every operation. A sensitive action whose choice or arguments derive from content the agent read (a tool output, a retrieved document, a web page, another agent) escalates (`provenance_flow: escalate: ... (prompt-injection path)`), and only a principal-signed escalation answer admits it; a forged, broken or unbound receipt chain denies; a read-only action is never sensitive and an undescribed action is. The labels come from signed receipts written by the agent harness: `ProvenanceRecorder` / `create_provenance_recorder` (`principal`, `tool`, `retrieval`, `web`, `for_action`, `pin`) and `principal_direct_provenance` on the agent side; the bundle travels in the `PCA-Provenance` header or the JSON body member `pca_provenance` (`read_provenance_bundle`; a header that does not decode is refused). New `authorize` / `AuthorizeOptions` members: `provenance`, `provenance_request`, `provenance_mediators`, `provenance_actions`, `provenance_observed`; `AuthorizeOptions.run(..., provenance=, request=)`. A plan authorized through `PlanRegistry` and an admitted workflow step count as the principal's choice. The grant envelope member `provenance` (`{"mode"?: "enforce" | "insecure_off", "mediators"?: [pin]}`, checked by `mint_grant`) designates mediators; `insecure_off` is the only opt-out (`not-enforced`). Also `decide_arg_provenance`, `occurs_as_token`, `prov_leaves`, `is_read_only_action`, `prov_action_digest`, `prov_receipt_ref`, `prov_envelope_error`. To upgrade, have the agent harness send a bundle and pin its key. Shared vectors: `arg-provenance-vectors.json` (`test_arg_provenance_vectors.py`, `test_provenance_flow.py`).
- **New (undo windows):** `authorize(undo_admit=...)` / `AuthorizeOptions.undo_admit`: an unanswered escalation that is not a provenance escalation can run now under a veto window. The hook `(pcactn, grant, operation) -> {"id", "window_end", "compensation": {"verb", "resource"}} | None` is never called for a provenance escalation, an answered call or a denial; a hook that raises or returns a malformed admission admits nothing. An admitted call is an allow with `checks["undo_window"] == "pass"`, `result.undo` and `result.obligations == [{"kind": "undo_window", ...}]` (new obligation kind `undo_window`, params `id`, `window_end`). The pure layer: `compensation_digest`, `sign_undo_token`, `undo_token_check`, `encode_undo_token`, `decode_undo_token`, `undo_token_digest`, `sign_undo_receipt`, `verify_undo_receipt`, `undo_receipt_digest`, `undo_receipt_chain_error`, `undo_transition`, `resolve_undo_window`. Shared vectors: `undo-vectors.json` (`test_undo_vectors.py`).
- **New:** `protect(audience, grants, operation, ...)` returns the options for the FastAPI / Django guards with secure defaults (grant list or function, in-memory replay store, `revoke()`, single-step plan); `explain_refusal(reason)` and `refusal_doc_url(reason)` (same table as the TypeScript `explainRefusal`); runnable `examples/fastapi-server`.
- **Changed (response bodies):** the Django middleware JSON gains `doc`. FastAPI `RequirePCA` keeps `detail` exactly as before (the reason string; the escalate object) and now raises `PCARefusal` (an `HTTPException` with a `.doc` attribute); call `add_pca_handler(app)` to also return `doc` as a sibling of `detail` in the body. Reason strings are unchanged.
- **New (native signing, agent side):** `atlas_pca.agent`, the producer half of the package, so an agent never needs a TypeScript process: Ed25519 keys (`generate_keypair`, `keypair_from_seed`), root grants (`mint_grant`: envelope, salted goal commitment, `holder_pq`), delegation (`delegate`, `attenuate`: append-only caveats, `sealed_caveat`, `max_uses_caveat`, `needs_discharge_caveat`), plan commitments with Merkle proofs (`commit_plan`), signed PCActns (`build_pcactn`, optional `intent`, `fresh_at`, `caution`, `tool_binding`, ...), the `PCA-Action` / `PCA-Discharges` / `PCA-Narrow` / `PCA-Escalation-Answer` headers (`pca_headers`), escalation answers (`sign_escalation_answer`, with `render_digest`), third-party discharges and narrow blocks, agent passports, workflow commitments and step receipts, signed read and aggregate grants and `fresh_at` tokens, and the `Agent` client (`act`, `delegate`, `use_plan`, `fetch`: counter, nonce and header handling). ML-DSA-65 / ML-DSA-87 and their hybrid and nested-hybrid suites sign through `dilithium-py` (extra `pq`); SLH-DSA-SHA2-128f / 256s sign through OpenSSL >= 3.5 (ctypes, `generate_pq_keypair`); FN-DSA and LESS are verify-only and raise `UnsupportedSuite`. Deterministic outputs reproduce the shared `producer-vectors.json` byte for byte (`test_agent_producer.py`, which also round-trips every artifact through this package's verifiers).

- **Breaking (K5, plan_root_authorized default-deny):** with no plan and no authorization supplied (`plan=None` and no `context` plan or `plans` registry), `authorize` now FAILS `plan_root_authorized` with `plan_root_authorized: default-deny: no authorized plan is configured for this verifier (supply the plan and its authorization, or set insecure_skip_plan_root_check)` instead of reporting `not-enforced` (which the required-check gate then refused with a different reason). `authorize` does not accept the opt-out `insecure_skip_plan_root_check`; this SDK's lower-level `verify_pcactn_core` does not compute `plan_root_authorized`, so it has no opt-out to carry.

- **New (K5, workflow through the guards):** `AuthorizeOptions.workflow` (and `workflow_step=(headers, body) -> step | None`) reaches `require_pca`, FastAPI `RequirePCA` and Django `PCAMiddleware` (`PCA_AUTHORIZE`). The step comes from the callback, else the JSON body member `workflow` (`extract_workflow_step`); refusals are `authorize`'s (403, `workflow: edge_relation (step pay)`). A configured `workflow` with `required` and no step is refused 403 BEFORE the PCActn is read, in `authorize` and in the guards (an undecodable PCActn with a step keeps the pipeline's own 401). Tests: `test_k5_middleware_workflow.py`.
- **New (K5, workflow admission inside `authorize`, C-308):** `authorize(workflow={"principal", "rs_signer", "required"?}, workflow_step={"commitment", "receipts", "step", "units"?, "goal_digest"?})` (also `AuthorizeOptions.workflow` and `AuthorizeOptions.run(..., workflow=<step>)`) runs `admit_step` for the operation the server will execute, with the presented PCActn's `plan.root`, BEFORE the core checks and the replay claim: a refusal (403, checks exactly `{workflow: fail}`, reason `workflow: <code> (step <id>)`; an escalate keeps `decision == "escalate"`) never consumes the counter, and a call without a step is refused only when `required` is `True`. Replays `authorize-workflow-fixtures.json` (`test_k5_authorize_workflow.py`).
- **New (K5, tokenisation vault and aggregate reads, C-315..C-319):** `atlas_pca.read_vault` (`memory_vault`, `redact_read_with_vault`, `detokenize`, `aggregate_read` over an explicit `{spent_micro, queries, answered}` state with k-minimum, clamp, query cap, integer micro-epsilon budget and free repeats, and the integer-exact discrete Laplace sampler `seeded_draws` / `secure_draws` / `discrete_laplace`; `secure` noise is the production setting). Total functions with the reference's check order and result shapes; integers only (a float or a bool is never an integer); unknown members deny. ## 0.4.1 - 2026-10-12

- Security (policy layer): caveats on the root grant outside the envelope are now evaluated like delegated caveats; new policy_caveats/evaluate_caveats helpers (incl. max_spend). The core verifier still does not evaluate caveats. `policy_caveats(grant, chain)` = the grant's caveats without its first `envelope` caveat, then the caveats the hops appended; `evaluate_caveats(caveats, ctx) -> (ok, failed)` is total. New corpus table `caveat_eval`.
- Threshold share signatures are validated per suite in `wire`: `alg` absent = ed25519 (64-byte `sig`, no `pq_sig`), `ml-dsa-65` (3309-byte `sig`, no `pq_sig`), `hybrid-ed25519-ml-dsa-65` (64-byte `sig` + 3309-byte `pq_sig`); a non-string or unknown `alg` fails. A share's `pq_pk` stays an optional echo judged by the threshold check. Before, every share `sig` had to be 64 bytes, so a pure ML-DSA-65 share could not be carried. New helper `validate_share_signature_wire`. The conformance runner skips vectors whose `requires` names a suite this package does not implement (ml-dsa-87, slh-dsa-sha2-128f).
- The `PCA-Action` header is decoded by the new public `decode_pca_header` (raises `PcaHeaderError`): strict unpadded base64url (no padding, standard alphabet or whitespace anywhere, nothing trimmed, canonical trailing bits) then strict UTF-8 with a leading BOM kept. The guard already decoded strictly; it now goes through this one decoder (same 401). New corpus table `pca_header`.

## 0.4.0 - 2026-10-11 (BREAKING)

- Depth / strict digests (security, parity): every protocol digest (`hash_canonical`: capability / grant hash, hop body digest, caveat comparison, params and conditions digests; Merkle leaves) now uses the STRICT canonical form like the reference (`hashCanonical` is `canonicalizeStrict`): nesting depth <= 32, safe integers only, plain decimals, no lone surrogates. It was the lenient form, so a correctly SIGNED hop carrying a depth-33 value, `1e300`, `2^53+2` or a lone surrogate verified although the reference refuses the chain (and the lenient form recursed without bound). Such hops are now refused (`hop N: malformed body`). `hash_canonical` raises `TypeError` on out-of-profile input, like the reference. `verify_leaf_suite` is total.
- R6-03 / R6-04 (security, parity): `verify_threshold_share` validates the WHOLE signer set like the TypeScript reference before looking at the share: unknown roles, non-canonical / non-32-byte public keys, and an empty, null, short or non-canonical `pq_pk` ANYWHERE in the set now refuse it; one key per role and one role per key; a duplicate (role, key) entry is accepted only with the same `pq_pk` (a conflicting one used to resolve first-wins); `t` must be 1, 2 or 3 (0..255 was accepted); `share.role` must equal the role. New corpus tables `threshold_set` / `signer_set_hash`.
- R6-05: `verify_chain`, `verify_threshold_share` and `verify_pcactn_core` are TOTAL: malformed input (non-object hop, missing or wrong-typed fields, truncated base64url, huge numbers) is a deny, never an exception. `verify_chain` also applies the reference hop type check (string id/issuer/holder/body_digest/sig, optional alg/pq_pk/pq_sig/holder_pq/parent absent or string, caveats a list of objects with a string `type`), so a correctly signed but ill-typed hop is now refused. New corpus table `malformed`.
- R6-02 (security): a signer-set role that registers a `pq_pk` now REQUIRES a PQ (pure or hybrid) threshold share; an ed25519-only share for that role is refused, so an Ed25519 break no longer forges a hybrid-registered role (parity with the TypeScript reference). Corpus: `agent-bound-signerset-with-pq-pk` is now `valid:false`; new positive `agent-hybrid-signerset-with-pq-pk`.
- R5-A1 (security): threshold-share verification is now signer-set PINNED, no longer self-vouched. The share must be for the one key the signer set registers for its role, a PQ/hybrid share verifies only under the set's registered `pq_pk` (a differing share `pq_pk` is refused), the share-suite tag is part of the signed bytes (a classical share cannot be relabelled hybrid), and the signer-set hash now includes a registered `pq_pk` (parity with the TypeScript reference). New corpus vectors: `agent-not-in-signer-set`, `agent-bound-signerset-with-pq-pk`, `agent-hybrid-relabel-*`.

- Suite policy defaults documented: no list = no restriction, an empty list refuses everything, and the hosted API defaults to ed25519 + Ed25519 hybrids (README lists the exact list to pass offline).

- R4-01: `verify_chain` now takes the root's PQ authority from the verifier, exactly like the TypeScript reference (R3-01). A non-ed25519 (pure `ml-dsa-65` or hybrid) ROOT hop is accepted only if the new `pq_pins` argument maps `root.issuer` to the root's own `pq_pk`, or the new `trusted_root` argument is the root itself (same content hash, i.e. the verifier's stored grant). Otherwise it is refused with `hop 0: root suite '<alg>' needs a PQ key pinned for the root issuer (policy.pqPins) or the verifier's stored grant (policy.trustedRoot); the root's own pq_pk proves nothing about who issued it (R3-01)`. Before, a pure-PQ root signed with the attacker's own ML-DSA key but naming a victim Ed25519 issuer verified. Callers of `verify_chain` on a root they did not load from their own store must now pass `pq_pins`. `verify_pcactn_core` is unchanged in behaviour (it passes its grant as `trusted_root`). Internally one `_resolve_pq_key` choke point mints the only key type `_verify_suite` accepts, so the PQ verify cannot be called with an artifact key.

- R3-03: the verifier now enforces the F-2 `holder_pq` binding exactly like the TypeScript reference. A hop (index >= 1) or the PCActn leaf signed under `ml-dsa-65` / `hybrid-ed25519-ml-dsa-65` is accepted only if its `pq_pk` hashes to the signer's `holder_pq` commitment; an unbound or attacker-chosen PQ key now fails (`chain` / `leaf_signature`). Hops may carry `holder_pq` (32-byte base64url, part of the signed body). New optional `allowed_suites` argument on `verify_pcactn_core` / `verify_chain` (a present list, even empty, enforces). Natives have no `allowUnboundPq` switch.
